# The publish pipeline regenerates CHANGELOG.md and loses the 0.1.0 section on a tagless repository

MEASURED, NOT HYPOTHETICAL, AND THE FRAMING MATTERS MORE THAN THE MEASUREMENT. (A NOTE ON THIS CARD'S OWN FRONTMATTER: it carries "status: tasked" and "mandate: true" beside "column: approval". That residue could NOT be cleared — the tool refuses those values in this zone — and it is left deliberately rather than hand-edited, so a reader knows the frontmatter is the tool's output, not a hand-tuned state. Most of the field set IS the tool's output from trddgrep new and trddgrep move; the "approved" field alone was changed by hand through trddgrep set, in both directions, while the column was being corrected.) This is not a defect in stage_changelog: that function does exactly what its own docstring says it does. It is a mismatch between a hand-authored file and a generator that will replace it, and a publish-path fact about where the first release tag should go.

THE REAL FINDING IS A FORMAT MIGRATION, NOT A PIPELINE DATA-LOSS DEFECT. The shipped CHANGELOG.md is HAND-AUTHORED, and it is in a DIFFERENT FORMAT from what the pipeline produces. Three checks establish that: the shipped file's header reads "The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)" while cliff.toml's own header template reads "All notable changes to this project will be documented in this file."; the shipped file carries a "## [Unreleased]" section, which is a shape cliff emits only for a version-less render; and the shipped file carries NO cliff footer, where cliff.toml's footer template ends every file it writes with "Generated by [git-cliff]". So there was never a cliff-generated 0.1.0 to lose. The correct statement of what a publish does is: IT REPLACES A HAND-AUTHORED KEEP-A-CHANGELOG FILE WITH A CLIFF-GENERATED ONE, and every hand-written sentence in it is lost.

THE REPOSITORY HAS NO TAGS (git tag returns 0; git describe fails). scripts/publish.py:2741 stage_changelog runs: git cliff --bump --tag v<NEXT> -o CHANGELOG.md, and -o OVERWRITES the file.

REPRODUCED on a clone of this repository (the working tree untouched). Running the pipeline's exact command produces a file with no 0.1.0 section, no "Initial packaging" sentence, and no "## [Unreleased]" section; the render begins at "## [0.2.0] - 2026-10-20" and derives every bullet from the commit log. The 0.1.0-era COMMITS all survive in the render (their short shas b2643d3, 1f57a97, 55b1820, e25b03e and 2c0e096 all appear) — the commits are not lost; the hand-written HEADINGS and PROSE are.

WHAT IS LOST, AND THAT IT IS NOT RECOVERABLE FROM THE COMMIT LOG. Three hand-written passages vanish: the 0.1.0 section's single bullet ("Initial packaging: the expert mods developer agent and 60 reference skills holding verbatim Claude Code documentation chapters"), and the two "## [Unreleased]" bullets ("Renamed 11 skills to drop the reserved words claude and anthropic and the vague word tools from their names." and "Every SKILL.md now embeds the full table of contents of its chapter."). The last two were NEVER in a commit message — a search of the whole commit log for them returns nothing — so unlike the commits, they are gone with no trace anywhere.

WHY THE 0.1.0 BULLET MATTERS TO THE ABSOLUTE-PATH SERIES SPECIFICALLY. That bullet says the chapters hold 'verbatim Claude Code documentation chapters'. The series established that word is WRONG (the chapters are adapted, not verbatim), and the correction was routed to the commit message because the file is regenerated by the pipeline and hand-written prose in it does not survive a publish. The next publish therefore does not erase the false word alone — it replaces the whole hand-authored file, and the false word leaves as collateral of a format migration rather than as a targeted correction. The correction in the commit message is still the right place for it; the series' original reasoning holds.

THE LOSS DOES NOT DEPEND ON WHERE THE RELEASE IS CUT. An earlier draft of this card said a release cut before e25b03e would yield a CHANGELOG with no 0.1.0 section. The measurement does not support that conditional and the conditional is RETIRED: the loss is unconditional, because cliff's output has no "## [0.1.0]" heading whichever commit the cut lands on — no cliff-generated 0.1.0 ever existed.

THE VERSION-BUMP PATH IS UNTESTED HERE. With no tag there is nothing for --bump to bump from; it warns "There is nothing to bump" and falls back to the supplied --tag. That warning is about VERSION DERIVATION, not about section preservation — the two are connected (no tag means no prior release boundary, so the whole history renders under one heading) but the warning is not the mechanism that drops the section.

WHAT TAGGING WOULD ACTUALLY DO — MEASURED, not assumed. A card that says "tag the repository" without saying what the render then looks like sends the reader in blind. Three cases were rendered on clones, with the pipeline's exact command: (a) NO TAG — the render begins at "## [0.2.0] - 2026-10-20" and carries the WHOLE history, 114 lines; (b) a tag at the ROOT commit — same shape, same 0.2.0 heading, same whole history, 116 lines; (c) a tag at an INTERMEDIATE commit — same shape, same 0.2.0 heading, 118 lines; (d) a tag at HEAD — the render STILL carries the whole history, root commit and HEAD commit both present, 114 lines. **SO TAGGING DOES NOT NARROW THE RENDER, AND IT DOES NOT PRODUCE AN EMPTY HISTORY.** The reason is that cliff.toml configures no commit RANGE, so cliff renders the whole history whatever tags exist; the tag affects only which heading cliff labels the window with. **AND THAT IS WHERE THE TAG CAN BE DANGEROUS. In case (d) — a tag at HEAD — cliff renders the heading "## [0.0.1] - 2026-10-20" while the pipeline passes it "--tag v0.1.1" (the version the pipeline actually computes, measured below). THE TWO DISAGREE: the file would claim the whole history IS release 0.0.1, dated today, under a version the pipeline did not intend.

**THE OBSERVED BEHAVIOUR, STATED AS WHAT WAS MEASURED.** With NO tag, the supplied "--tag v0.9.9" is used ("## [0.9.9]"); with a tag at an EARLIER commit, the supplied tag is STILL used ("## [0.9.9]") and the render still carries the whole history; with a tag AT the commit being released, cliff warns "There is already a tag (v0.0.1) for <sha>" and labels the window with the EXISTING tag instead ("## [0.0.1]").

**THE FIVE CASES, AS MEASURED** (case / tag position / supplied --tag / rendered heading / bullets):

| case | tag position | supplied `--tag` | rendered heading | bullets |
|---|---|---|---|---|
| (a) | no tag at all | v0.9.9 | `## [0.9.9]` | 87 |
| (b) | root commit | v0.9.9 | `## [0.9.9]` | 87 |
| (c) | an intermediate commit | v0.9.9 | `## [0.9.9]` | 87 |
| (d) | the commit being released (HEAD) | v0.9.9 | `## [0.0.1]` | 86 |
| (e) | a commit on ANOTHER BRANCH, not the released one | v0.9.9 | `## [0.9.9]` | 89 |

**WHAT THE CASES SHOW, AT THE STRENGTH THEY SUPPORT.** In every case where the tag was NOT on the commit being released, the supplied tag was used; in the one case where it was, the existing tag was used. **The earlier draft of this card stated this as a NECESSARY CONDITION — "the mismatch appears only when a tag sits ON the commit being released" — and that is withdrawn, because the cases do not isolate it.** Case (e) was added specifically to try to discriminate, and it does not: a tag on a different branch is also unaffected. **THE RULES THE MEASUREMENT LEAVES OPEN ARE SEVERAL — "a tag on the released commit", "a tag on HEAD", "the nearest tag", "the highest-version tag" — and the five cases are consistent with all of them.** A case that would discriminate them is a tag on the released commit whose version is NOT the highest in the repository; none was run. (The earlier draft of this card also said cliff "falls back to the supplied --tag only when none exists", which asserts a rule about tag EXISTENCE that the cases contradict twice over — cases (b) and (c) have a tag and still used the supplied one. Withdrawn.)

**AND THE ONE CONTENT DIFFERENCE THE CASES MEASURED, which is the most direct evidence that the tag's POSITION does not change WHAT IS RENDERED.** Case (d) has 86 bullets where cases (a), (b) and (c) have 87; the extra bullet in the unaffected cases is the tag commit itself, which case (d) excludes by definition. The rendered CONTENT is the same history in every case; only the heading string changes. That is why the finding below is a heading-label matter, not a scope matter.

**AND THE PIPELINE'S OWN STEP ORDER MAKES THE PRECONDITION REACHABLE.** stage_changelog is step 13 and stage_commit_and_push (which creates the release tag) is step 14 — so the changelog is rendered BEFORE this publish's tag exists. The precondition is a tag sitting ON the commit about to be released. **AN EARLIER DRAFT OF THIS CARD SAID THE HAZARD "FIRES ON THE SECOND RELEASE" — THAT IS WITHDRAWN, and the card's own case table contradicts it**: after a first release, the first release's tag sits on the FIRST release's commit, which is an EARLIER commit relative to the second release, and the measurement says that case is UNAFFECTED. What the step order does establish is that the tag for the release being cut is created AFTER the changelog is rendered, so the tag that could collide is always a LEFTOVER one. When a leftover tag ends up on the commit being released — a re-release of an already-tagged commit, or a tag placed at HEAD by hand — the mismatch fires. WHICH RELEASE IT FIRES ON IS NOT ESTABLISHED, and this card does not predict it.

THE VERSION THE PIPELINE ACTUALLY COMPUTES HERE — MEASURED, because the constraint below turns on it, and its BASELINE is measured too so the number is earned. The pipeline's detect_next calls "git-cliff --bumped-version"; on this TAGLESS repository that command does not merely warn, it FAILS — it reports "No releases found, using 0.1.0 as the next version" on STDERR and then exits non-zero with "Next version (0.1.0) does not match the tag pattern: v[0-9].*". Its STDOUT is empty, so detect_next's own guard "if not bumped or bumped == current: return patch" applies. The baseline is "_read_remote_version(root) or get_current_version(root)", and **THIS REPOSITORY HAS NO GIT REMOTE AT ALL — "git remote -v" prints nothing — so every ref that function tries (origin/master, origin/main, origin/HEAD) is unresolvable, it returns None, and the baseline is the LOCAL .claude-plugin/plugin.json, whose version is 0.1.0.** bump_semver("0.1.0", "patch") is therefore 0.1.1. **So the version this card earlier asserted — 0.2.0 — was NOT MEASURED and was in fact WRONG; the pipeline would pass "--tag v0.1.1".** Every step of that chain is measured, and the repository's lack of a remote is what pins the baseline to the local value.

THE REASSURING CASE, which keeps the finding proportionate. The mismatch is a NARROW ANOMALY, not a systemic one. On the FIRST release the render labels the window from the SUPPLIED tag, and the supplied tag is built from the version the pipeline computed — so the two agree by construction. On later releases, once a tag exists, the computed version is derived FROM a tag and the label is taken FROM a tag — so they agree again IN THE ORDINARY CASE, WHERE THE RELEASE TAG IS ALSO THE MOST RECENT TAG. That uniqueness is not guaranteed: if a stale tag sits on the released commit while a newer tag sits elsewhere, the label comes from the stale one and the version from the newer one, and they disagree. The mismatch requires a tag ON the commit being released whose version DIFFERS from the computed one. Everything else measured — no tag, a tag at the root, a tag at an earlier commit — produced a correct label.

THE SCOPE FACT, WHICH IS THE MORE CONSEQUENTIAL HALF. cliff.toml configures no commit RANGE, so the render is not a release window at all — it is EVERY COMMIT EVER, under one dated heading. cliff.toml's body template does contain an "## [Unreleased]" branch, but it is unreachable on this pipeline: the template emits it only when the version is absent, and stage_changelog always passes "--tag". So the changelog's SHAPE is an invocation choice, not a property of the tool: THE CURRENT CONFIGURATION renders the whole history, wherever it was measured. (An earlier draft of this card said the pipeline "has never produced a release-scoped changelog" — a claim about every past run, which four renders on clones do not establish; what the measurement shows is what the CURRENT configuration does.) **AND THE TEMPLATE'S "## [Unreleased]" BRANCH IS BETTER READ AS A REMNANT THAN AS DEAD CODE**: it is reachable in the template and unreachable only because stage_changelog always passes --tag, and the shipped hand-authored file is in exactly the shape that branch produces. The shipped hand-authored file may simply have followed the Keep a Changelog CONVENTION — which is a different claim from the pipeline once producing that shape, and the card does not assert the latter. Whether the right fix is to restore that invocation or to accept the new one is a question this card does not answer.

WHAT IS PROPOSED, AND WHAT IS NOT. Nothing is proposed beyond recording the finding, because what to do about it is a publish-path decision and it is the owner's. The question is not "how does cliff preserve a section it never had" but two questions: SHOULD THIS REPOSITORY BE TAGGED, and SHOULD THE HAND-WRITTEN RELEASE PROSE BE MOVED somewhere the pipeline does not overwrite. On the first: creating the first tag is OUTWARD-FACING (a later push of tags publishes it) and it decides WHERE 0.1.0 ENDS AND 0.2.0 BEGINS, so it is not merely "one command" — it is one command with a semantic choice inside it. On the second: stage_changelog's own docstring already states the constraints (-o overwrites, --unreleased truncates to only the new release, --prepend accumulates), so the obvious implementations of "preserve the prior section" inside that step are already ruled out by its own analysis. **AND THE CHEAPEST AVAILABLE ANSWER IS ALREADY PROVEN IN THIS REPOSITORY**: hand-written release prose can simply go into a commit message, which is where the series put the correction to the false word, and from where cliff will render it. That pattern is the repository's own, and it costs nothing.

REPRODUCTION (read-only, on a clone in /tmp, not on the working tree): git clone <this repo> /tmp/cliff-test; cd /tmp/cliff-test; git cliff --bump --tag v0.2.0 -o /tmp/cliff-out.md; grep -c 0.1.0 /tmp/cliff-out.md  # 0.
