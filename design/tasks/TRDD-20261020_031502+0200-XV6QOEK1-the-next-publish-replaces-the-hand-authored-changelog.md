# The publish pipeline regenerates CHANGELOG.md and loses the 0.1.0 section on a tagless repository

MEASURED, NOT HYPOTHETICAL, AND THE FRAMING MATTERS MORE THAN THE MEASUREMENT. **EVERY MEASUREMENT IN THIS CARD IS OF THE
PRE-TAG, NO-REMOTE STATE** — a repository with no git remote and no tags — and that is the state BEFORE the action the card describes.
Creating the first release tag and publishing it changes both the tag set and (if the repository is given a remote) the version
baseline, so the render measured here is the render BEFORE, not the render after. **WHICH FINDING THIS CARD IS ABOUT: the title names the FORMAT MIGRATION — the next publish replaces a hand-authored
CHANGELOG.md with a cliff-generated one, and every hand-written passage in it is lost. THAT is the finding the card is about, and it
is the one this card is about. **WHICH OF THE TWO IS MORE URGENT IS THE OWNER'S JUDGEMENT, NOT THIS CARD'S** — the plugin records what
each is, and does not rank them. **FOR THE BOARD'S SAKE, THE PRECEDENCE IS BY DEPENDENCE, NOT BY URGENCY: this card comes FIRST, because
it describes the FORMAT the file is in and the LOSS of what is in it, and TRDD-XY45DGD4 describes how a pre-existing tag re-sections
that render — a question about a render that only exists once this card's migration has happened. That is a dependency order, not a
priority claim, and it does not say which of the owner's two questions matters more. The version-label and section-structure material was a SECOND, SEPARATE finding and has now been
SPLIT OUT INTO ITS OWN CARD, TRDD-XY45DGD4, because it is a different subject and because eleven rounds of review had grown it inside
a card whose title names something else. This card keeps the format migration; the other card keeps the sectioning and the heading
label, and states the owner's question without classifying its significance. **This card does NOT classify
how much that matters.** An earlier draft of this card called that material "an ASIDE ... which the card itself calls cosmetic", and
that label is WITHDRAWN: it is a severity judgement the plugin has no remit to make, and it is the same class of move the series
retracted in the other direction when it called the false CHANGELOG word "a documentation defect rather than a policy question in
disguise". The measurement stands; the significance is the owner's to set.**
(A NOTE ON THIS CARD'S OWN FRONTMATTER: it carries "status: tasked" and "mandate: true" beside "column: approval". That residue could NOT be cleared — the tool refuses those values in this zone — and it is left deliberately rather than hand-edited, so a reader knows the frontmatter is the tool's output, not a hand-tuned state. Most of the field set IS the tool's output from trddgrep new and trddgrep move; the "approved" field alone was changed by hand through trddgrep set, in both directions, while the column was being corrected.) This is not a defect in stage_changelog: that function does exactly what its own docstring says it does. It is a mismatch between a hand-authored file and a generator that will replace it, and a publish-path fact about where the first release tag should go.

THE REAL FINDING IS A FORMAT MIGRATION, NOT A PIPELINE DATA-LOSS DEFECT. The shipped CHANGELOG.md is HAND-AUTHORED, and it is in a DIFFERENT FORMAT from what the pipeline produces. Three checks establish that: the shipped file's header reads "The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)" while cliff.toml's own header template reads "All notable changes to this project will be documented in this file."; the shipped file carries a "## [Unreleased]" section, which is a shape cliff emits only for a version-less render; and the shipped file carries NO cliff footer, where cliff.toml's footer template ends every file it writes with "Generated by [git-cliff]". So there was never a cliff-generated 0.1.0 to lose. The correct statement of what a publish does is: IT REPLACES A HAND-AUTHORED KEEP-A-CHANGELOG FILE WITH A CLIFF-GENERATED ONE, and every hand-written sentence in it is lost.

THE REPOSITORY HAS NO TAGS (git tag returns 0; git describe fails). scripts/publish.py:2741 stage_changelog runs: git cliff --bump --tag v<NEXT> -o CHANGELOG.md, and -o OVERWRITES the file.

REPRODUCED on a clone of this repository (the working tree untouched). Running the pipeline's exact command produces a file with no 0.1.0 section, no "Initial packaging" sentence, and no "## [Unreleased]" section; the render begins at "## [0.2.0] - 2026-10-20" and derives every bullet from the commit log. The 0.1.0-era COMMITS all survive in the render (their short shas b2643d3, 1f57a97, 55b1820, e25b03e and 2c0e096 all appear) — the commits are not lost; the hand-written HEADINGS and PROSE are.

WHAT IS LOST, AND THAT IT IS NOT RECOVERABLE FROM THE COMMIT LOG. Three hand-written passages vanish: the 0.1.0 section's single bullet ("Initial packaging: the expert mods developer agent and 60 reference skills holding verbatim Claude Code documentation chapters"), and the two "## [Unreleased]" bullets ("Renamed 11 skills to drop the reserved words claude and anthropic and the vague word tools from their names." and "Every SKILL.md now embeds the full table of contents of its chapter."). The last two were NEVER in a commit message — a search of the whole commit log for them returns nothing — so unlike the commits, they are gone with no trace anywhere.

WHY THE 0.1.0 BULLET MATTERS TO THE ABSOLUTE-PATH SERIES SPECIFICALLY. That bullet says the chapters hold 'verbatim Claude Code documentation chapters'. The series established that word is WRONG (the chapters are adapted, not verbatim), and the correction was routed to the commit message because the file is regenerated by the pipeline and hand-written prose in it does not survive a publish. The next publish therefore does not erase the false word alone — it replaces the whole hand-authored file, and the false word leaves as collateral of a format migration rather than as a targeted correction. The correction in the commit message is still the right place for it; the series' original reasoning holds.

THE LOSS DOES NOT DEPEND ON WHERE THE RELEASE IS CUT. An earlier draft of this card said a release cut before e25b03e would yield a CHANGELOG with no 0.1.0 section. The measurement does not support that conditional and the conditional is RETIRED: the loss is unconditional, because cliff's output has no "## [0.1.0]" heading whichever commit the cut lands on — no cliff-generated 0.1.0 ever existed.

THE VERSION-BUMP PATH IS UNTESTED HERE. With no tag there is nothing for --bump to bump from; it warns "There is nothing to bump" and falls back to the supplied --tag. That warning is about VERSION DERIVATION, not about section preservation — the two are connected (no tag means no prior release boundary, so the whole history renders under one heading) but the warning is not the mechanism that drops the section.

THE SECTION-STRUCTURE AND VERSION-LABEL MATERIAL HAS MOVED OUT OF THIS CARD into TRDD-XY45DGD4, which is the authoritative record for it: the five-case table, the controlled experiment, the diff, the mechanism, the baseline derivation and the warning-column inference all live there now. This card keeps the FORMAT MIGRATION — the next publish replaces a hand-authored CHANGELOG.md with a cliff-generated one, and every hand-written passage in it is lost — which is the finding the title names. **THE ONE FACT THIS CARD STILL NEEDS FROM THAT MATERIAL**: the version the pipeline computes here is 0.1.1, because the repository has no remote and no tag, so the baseline is the local plugin.json at 0.1.0 and the bump is a patch — which is the version any first tag would have to match. That derivation is in the next section. And the LABELLING RULE it leans on — that cliff labels the window from a tag that already exists on the commit it is labelling, and falls back to the supplied tag only when none does — is measured, with its cases, in TRDD-XY45DGD4.

THE VERSION THE PIPELINE ACTUALLY COMPUTES HERE — MEASURED, because the version any first tag would have to match turns on it, and its BASELINE is measured too so the number is earned. The pipeline's detect_next calls "git-cliff --bumped-version"; on this TAGLESS repository that command does not merely warn, it FAILS — it reports "No releases found, using 0.1.0 as the next version" on STDERR and then exits non-zero with "Next version (0.1.0) does not match the tag pattern: v[0-9].*". Its STDOUT is empty, so detect_next's own guard "if not bumped or bumped == current: return patch" applies. The baseline is "_read_remote_version(root) or get_current_version(root)", and **THIS REPOSITORY HAS NO GIT REMOTE AT ALL — "git remote -v" prints nothing — so every ref that function tries (origin/master, origin/main, origin/HEAD) is unresolvable, it returns None, and the baseline is the LOCAL .claude-plugin/plugin.json, whose version is 0.1.0. (The general rule is "the remote lookup returned nothing", which also holds for a repository that HAS a remote but is offline or lacks such a ref; the local fact measured here is the stronger and simpler one — there is no remote to look at.)** bump_semver("0.1.0", "patch") is therefore 0.1.1. **So the version this card earlier asserted — 0.2.0 — was NOT MEASURED and was in fact WRONG; the pipeline would pass "--tag v0.1.1".** Every step of that chain is measured, and the repository's lack of a remote is what pins the baseline to the local value.

THE SCOPE FACT, WHICH IS THE MORE CONSEQUENTIAL HALF. cliff.toml configures no commit RANGE, so the render is not a release window at all — it is EVERY COMMIT EVER, under one dated heading. cliff.toml's body template does contain an "## [Unreleased]" branch, but it is unreachable on this pipeline: the template emits it only when the version is absent, and stage_changelog always passes "--tag". So the changelog's SHAPE is an invocation choice, not a property of the tool: THE CURRENT CONFIGURATION renders the whole history, wherever it was measured. (An earlier draft of this card said the pipeline "has never produced a release-scoped changelog" — a claim about every past run, which four renders on clones do not establish; what the measurement shows is what the CURRENT configuration does.) **AND THE TEMPLATE'S "## [Unreleased]" BRANCH IS BETTER READ AS A REMNANT THAN AS DEAD CODE**: it is reachable in the template and unreachable only because stage_changelog always passes --tag, and the shipped hand-authored file is in exactly the shape that branch produces. The shipped hand-authored file may simply have followed the Keep a Changelog CONVENTION — which is a different claim from the pipeline once producing that shape, and the card does not assert the latter. Whether the right fix is to restore that invocation or to accept the new one is a question this card does not answer.

WHAT IS PROPOSED, AND WHAT IS NOT. Nothing is proposed beyond recording the finding, because what to do about it is a publish-path decision and it is the owner's. The question is not "how does cliff preserve a section it never had" but two questions: SHOULD THIS REPOSITORY BE TAGGED, and SHOULD THE HAND-WRITTEN RELEASE PROSE BE MOVED somewhere the pipeline does not overwrite. On the first: creating the first tag is OUTWARD-FACING (a later push of tags publishes it) and it decides WHERE 0.1.0 ENDS AND 0.2.0 BEGINS, so it is not merely "one command" — it is one command with a semantic choice inside it. On the second: stage_changelog's own docstring already states the constraints (-o overwrites, --unreleased truncates to only the new release, --prepend accumulates), so the obvious implementations of "preserve the prior section" inside that step are already ruled out by its own analysis. **AND THE CHEAPEST AVAILABLE ANSWER IS ALREADY PROVEN IN THIS REPOSITORY**: hand-written release prose can simply go into a commit message, which is where the series put the correction to the false word, and from where cliff will render it. That pattern is the repository's own, and it costs nothing.
