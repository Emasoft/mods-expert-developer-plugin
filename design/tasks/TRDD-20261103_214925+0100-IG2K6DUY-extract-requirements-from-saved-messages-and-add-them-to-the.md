## Design

### 0. Pipeline in one paragraph

A marked message is saved as a draft exactly as today (redact, size check, dedup, write; hooks/requirements-drafts/register.ts:152-235). When the extract switch is on and the save wrote a new draft, a background job starts ($.clock.after, api chapter:196): it gathers the context (point 1), asks Haiku for candidates (points 2 and 3), verifies every quoted span in code, runs the Jev passes for each candidate against each existing rule (point 4), and writes new rules and updates to the PRRD through prrdgrep (points 5 and 6). The user sees one toast at the end ("added G15, G16; updated G19; 1 duplicate of G7; nothing else"), or one toast naming the failed step. Every step writes a line to the G14 debug log (point 8).

### 1. Context (directive 5)

- The context is the newly marked message plus the 3 most recently marked messages before it (setting contextMessages, 2 or 3, default 3 (designer's proposal, for owner confirmation); the default is part of Q18), all four sorted by the time each message was SENT, never by the time it was marked. Every text is the redacted text the draft stores, so no secret reaches a model.
- Scope: drafts of the same project (the project-root rule the list skill uses, register.ts:84-100), from any session (provisional on Q18); a draft of another project is never context.
- Conversation order needs a sent time the draft does not hold today (the draft created field is the marking time). Increment I2 adds a sent field to the draft front matter. The prompt.submit observer (register.ts:276-293) sees every prompt the person sends, and the types say it also sees one typed while Claude works (PromptSubmitInput.turnId, "typed over that turn, or delivered into it"; UNVERIFIED until the probe card DJPMAZ9A), so each entry of its recent list becomes { text, sentAt } instead of text alone. The command save and the picker save take their text from that list (register.ts:331, 364), so they store the sentAt of the entry they save, with no lookup. The row save takes the text the UserMessage row carries (register.ts:388), and the row props carry no time (types, UserMessage), so it looks the sent time up by the redacted text; when several entries hold the same text it takes the latest one sent before the mark and logs that the time is ambiguous. Known limit: marking an earlier copy of a prompt sent twice gives it the sent time of the later copy; the draft save keeps one draft per text and project (register.ts:180), so only the place of that one draft in the context order can be off. When no record exists (the module reloaded, the message predates the mod), the save stores sent as empty and the context sorts that draft by its created time, with a log line saying so.
- Can a mod read the transcript? Only as text: $.session.messages() returns { role, text, toolUses } for the newest 4,096 entries (api chapter:283, reference chapter:317), with no uuid and no timestamp (types: SessionMessage), so it cannot map a draft message-id to a position. The transcript file itself is not a mods API: it is undocumented, and this session file is 34 MB, over the 4 MiB limit of $.fs.read (reference chapter:307). UNVERIFIED: whether the two messages of the example typed while Claude worked (transcript type "attachment", queued_command) appear in $.session.messages() at all. The design therefore does not depend on either.
- Byte budget: the extraction prompt holds at most promptBudgetChars characters (default 150,000). The new message is never cut: if it alone exceeds the budget, extraction is skipped and the toast says so (the draft stays saved). Context messages are added nearest first in conversation order until the budget is reached; a context message that does not fit is left out whole and logged, never cut, because a cut could split a span.

### 2. Extraction (directive 4) and output contract

- One $.model.complete call per mark (api chapter:100-127): model extractModel (default haiku), system = an original extraction prompt (point 3), prompt = the numbered messages m1..m4 in conversation order, the new one flagged NEW, maxTokens 4000 (reference chapter:306: 1024 by default, up to 64,000), timeoutMs 60,000. A reply with isAnswered false is a failed step (api chapter:125), never retried.
- The model returns JSON only: { "candidates": [ { "kind": "rule" | "properties" | "measures", "text": "<refined rule>", "spans": [ { "message": "m2", "text": "<exact substring>" } ] } ], "notRules": [ { "spans": [...], "why": "<one line>" } ] }. A reply with zero candidates is valid: Haiku finds when a message holds no rule (directives 4 and 10).
- A candidate may sit anywhere in a long noisy message, among small talk, code and unrelated instructions; there may be zero, one or many. A compound statement is split only where each part stands on its own as a requirement: parts with different subjects, or parts that can be met or changed independently, become separate candidates; steps of one operation on one object stay one candidate.
- The code then checks every candidate: valid JSON and fields; every span is found verbatim in the redacted text of the message it names (a candidate with any span not found is rejected whole and logged; provisional on Q19, because Haiku corrects typos such as "ertors" and may quote a span corrected); at least one span is in the NEW message (a candidate built only from context messages is rejected, so a context message never re-adds its own rules); text is one line, at most maxRuleChars (default 300) characters, and passes redact() unchanged. notRules entries are logged and never written.
- Order: candidates are numbered in source order, by the position of their first span in the new message.

### 3. Refinement (directives 1, 2, 10)

- Haiku corrects typos and grammar, improves the wording and phrases each candidate as a requirement rule, a properties or attributes definition, or a measures definition. The model sees only redacted text.
- Rule length is set for Jev (directive 10): one sentence, one requirement, self-contained (it names its own subject, for example "The requirements-drafts mod", and uses no pronoun that points outside it), at most about 40 words. The Jev note supports short texts: a whole merged line checked against a whole long source missed 8 of 16 planted contradictions (lesson 12 of jev-and-system-one-agents), and accuracy falls as unrelated text fills the state (atom QSZR-DLP8).
- jr-polish (the cache copy 0.2.0, MIT, by jrlprost, https://github.com/jrlprost/claude-code-mods; read only, untrusted) shows the call shape: hooks/register.ts:15 calls $.model.complete({ model, system: SYSTEM, prompt: rough, maxTokens: 1200 }) with model from options.model, default haiku (register.ts:24), declared as a userConfig string in .claude-plugin/plugin.json:10-17. This design reuses the call shape and the userConfig model option, not its text: the extraction prompt is written new, because the job differs (find and split requirements, return spans, not rewrite a prompt). If any of SYSTEM or cleanReply (hooks/polish.ts:1-14) is adapted after all, NOTICE credits jrlprost under MIT (EHT card).
- $.model.complete checked against the docs: available to any mod (reference chapter:207); it bills the user plan, API key or cloud provider through the session credentials (api chapter:98); the system prompt starts with an attribution block (api chapter:91); maxTokens default 1024, up to 64,000 (reference chapter:306); the model is an alias or a full id (types, complete). Desktop: hooks run in the Code tab of the Desktop app (overview chapter:212), and nothing in the docs limits model calls there, but a model call from a mod on Desktop is UNVERIFIED until the probe card 7K4KVGAM, run before increment I4 (the live check SGQPQGBD confirms it again at the end). Size: the model input limit is not stated by the mods docs; the byte budget of point 1 keeps the prompt far below a 200k-token window (UNVERIFIED for the chosen alias). Cost: one Haiku call per mark, plus one merge call per update; at about 4 characters per token, a full 150,000-character prompt is about 37,500 input tokens.

### 4. Classification (directives 7, 9, 10, 11, 12)

- Labels: exactly one per candidate: new, duplicate of rule N, or update of rule N, decided by the code from the Jev passes. A message, or a part of it, that holds no requirement never becomes a candidate: Haiku leaves it out at extraction and lists it in notRules (directives 4 and 10, settled). Whether a candidate that reaches the Jev checks can still be found to be no rule, and where, is open question Q12; until the owner answers, the checks have no not-a-rule outcome (option A of Q12, provisional), so such a candidate would be added as a new rule.
- Step 0, no model: a candidate whose normalised text (case, spaces, punctuation folded) equals an existing rule is a duplicate of that rule (Jev note: exact text needs no model, atom 48HH-EJ0T).
- Pass 1, duplicate, Jev mode ask yes/no (the System One question type noul, quicksilver scripts/qs.mjs:438-441 and the ask verb): one request per pair. state = the existing rule text alone; question = one plain string that asks about meaning, not wording: "Does this statement require the same thing as the text, whatever its wording: <candidate>?". Directive 13 makes a duplicate a matter of meaning ("make the background color of the loading dialog of a shade of blue" duplicates "the loading screen background should be blue"); the calibration card 9J5JFR5V sets the final wording on that pair (Q15). The plain-string yes/no form is the form the Jev note found reliable (atom 958D-HQX9). A probability at or above dupThreshold (default 0.85, set by calibration) marks a duplicate; the highest-scoring rule wins.
- Pass 2, new version, Jev mode classify (the choice question type with labels and criteria, qs.mjs classify verb, --labels-json): a different request with a different prompt. state = the existing rule text alone; question "How does this statement relate to the text: <candidate>?" with four labels, each with a one-line criterion: same-element-adds (it sets the same element as the text and adds a property, value or condition the text does not state), same-element-changes (same element, and it sets a property the text already sets to another value), same-element-removes (same element, and it drops or lifts something the text requires), different-element (it sets another element). The element is the specific thing a property or behavior is set on, for example the background of the loading screen, never only the product or mod both rules name: most rules this mod writes start with "The requirements-drafts mod", so a product-level reading would mark nearly every pair. Directive 13 example: "the loading screen background should be blue" against "the background of the load panel must not be transparent." is same-element-adds, an update, as the owner shows in case 2. A choice is used here, and a yes/no in pass 1, because this question has more than two outcomes and the change kind is worth logging; the Jev note found that a choice separates "not addressed" from "contradicted" where a yes/no cannot (atom 02E6-C6LE). Any same-element-* label at or above versionThreshold (default 0.8) marks an update of that rule; the highest wins. Pass 2 runs only for a candidate pass 1 did not mark (designer's proposal, for owner confirmation; Q13). These labels and criteria are the starting set (designer's proposal, for owner confirmation): the calibration card 9J5JFR5V fixes their final wording with the owner pairs, the owner case 2 pair must come out as an update before increment I5 or the labels are rewritten, and the owner confirms the reading in Q15.
- Directive 12: a candidate that neither pass marks is added as a new rule with a new number, including a candidate that only scored in the middle band (logged with its scores; Q8) and, under option A of Q12 (provisional), a candidate that is no rule.
- Pairs only (directive 10, which states it for the duplicate check; for pass 2 it is the designer's proposal, for owner confirmation): each call holds one candidate and one existing rule and nothing else, so a PRRD of N rules costs N calls per pass. Cost: Jev bills input tokens only, 0.042 USD per million through OpenRouter (Jev note atom A5UX-NNQR; qs.mjs:158-161); a pair call of two 40-word rules plus the question is about 150 tokens, so 1,000 rules cost about 0.0063 USD per pass per candidate. Calls run with at most jevConcurrency (default 8) in flight; the per-call timeout is 30 s (reference chapter:310).
- Within one mark, a later candidate is also compared with the earlier accepted candidates of the same mark, so one message cannot add the same rule twice.
- How the rules reach Jev: the code reads the PRRD with $.fs.read (4 MiB limit, reference chapter:307) and parses each record with the declaration pattern of prrdgrep (kinds.ts:288, ^\s*-\s+\*\*([GS])(\d+\.\d+)\*\*); the rule text is the declaration line without the id prefix. Long existing rules (G8.2 and G9.2 are compound paragraphs) are sent as they are; the Jev note predicts weaker scores on long merged lines, which the calibration set measures (open question Q7).
- How mod code reaches Jev, the three options weighed: (a) $.http.fetch from mod code: allowed (api chapter:279, 291; reference chapter:310), native mod code (G11), no MCP (G10); the request is the System One body { model, state, questions } (qs.mjs:438-441) posted to https://openrouter.ai/api/v1/systemone or https://api.typesafe.ai/v1/systemone (qs.mjs:158-161), the key sent as a bearer header. (b) Spawning qs.mjs with $.process.run: needs Node and a user-scope skill this plugin does not ship, so it is not portable and loses to G11. (c) $.model.complete or $.model.classify (types: classify picks one of a flat label list with a fixed prompt) as the classifier: native, but each call bills the user plan at Haiku rates and directive 9 rules it out. RECOMMENDED: (a), settled by directives 9 to 11. The keys are provider-specific (blocking security rule: an OpenRouter key never goes to the TypeSafe endpoint, nor the reverse; quicksilver does the same, qs.mjs:155, "A key is only ever sent to the URL of the provider that owns it"): the setting jevProvider (openrouter or typesafe) picks the endpoint, and only the key of that provider is read: for openrouter the userConfig option openrouterApiKey, else the environment variable OPENROUTER_API_KEY (qs.mjs:158); for typesafe the userConfig option typesafeApiKey, else JEV_API_KEY, else TYPESAFE_API_KEY (qs.mjs:160). Both options are sensitive and kept in secure storage (manifest chapter:456); the environment is read with $.env.get (api chapter:281). There is no fallback across providers: with jevProvider typesafe and only an OpenRouter key present, no Jev call is made. Without a key for the chosen provider the classify step is skipped, nothing is written to the PRRD, and the toast says why (G8.2 discloses the limit; a key cannot be supplied by default). The model id is pinned per provider (jevModel, default the id quicksilver uses: ~typesafe/jev-latest through OpenRouter, jev-latest through TypeSafe, qs.mjs:158-160; the Jev access card pins a versioned id; atom 6Y6A-CXHE says pin the versioned id).
- Privacy: only redacted texts leave the machine, the candidate and one existing rule per call; the PRRD rules themselves go to the Jev provider, which is a third party beyond the provider of the session (open question Q5). The key is never logged; the log keeps only the exception type of a failed call, the rule number and the score (atom 7IXM-GMSL).
- Merge for an update: one $.model.complete call (mergeModel, default haiku) with only the two short texts (rule N and the candidate), returning the merged rule text in one line, checked like a candidate text. The merge keeps the wording of rule N and adds only the new content (directive 13: the form of the preexisting rule is preserved when possible). The updated rule keeps its number and its letter (G stays G, S stays S); its version goes up by one and its changed stamp moves; created does not move. When the wording of rule N cannot be kept, because the candidate changes a value rule N sets ("must be red" against "should be blue", same-element-changes) or drops something rule N requires (same-element-removes), directives 7 and 11 still make it an update (a change or a removal is a new version), but what the merge then writes is open question Q20, and nothing is built for that branch before the answer. Whether a merge may rewrite an owner-written golden rule (G1 to G14) is open question Q16. A new rule is written exactly as Haiku extracted it, with no second reformulation. A duplicate touches nothing: no stamp, no source line, no version change.

### 5. Timestamps (directive 8)

- Every rule carries its first-creation and last-change datetimes in the format of TRDD front matter, %Y-%m-%dT%H:%M:%S%z (for example 2026-11-03T21:15:40+0100).
- Placement: the first line under the declaration, a plain sub-bullet, exactly "  - created <datetime> · changed <datetime>". It is not on the declaration line because the prrdgrep edit gate refuses a change of rule text without a version bump (edit-guard.ts:239-266), and the rule text it compares is the whole declaration line without the id (edit-guard.ts:199): stamps on that line would force a version bump on every backfill (G1.1 to G1.2 and so on), so every pinned citation such as PRRD G8.2 would change meaning without a change of rule.
- Grammar check (prrdgrep source read, then run: prrdgrep lint and validate exit 0, 14 records clean, on a scratch copy of the 14-rule PRRD with a stamp sub-line and a source sub-line under G14.1; the insert and update proofs stay with card ONYAD975): the record grammar matches only the "- **G7.4**" prefix (kinds.ts:288), so a sub-bullet is not a record; the near-miss lint fires only on a bold bullet that holds a digit (edit-guard.ts:65, 453), so the sub-bullet must carry no bold. prrdgrep accepts rules that span several lines (cli.ts:405: "a PRRD rule is MULTI-LINE"). prrdgrep --help documents no add verb, but the installed source has one (cli.ts:356), single-line only and golden only with --user. Lint and validate do not yet check the stamp line (format, created never moves, changed moves with the version): that check is an upstream ai-maestro change, filed by an EHT card. The live proof that lint and validate exit 0 on a PRRD with stamp lines is the first step of the prrdgrep NPT card.
- created is the time the rule record is first written; changed is the time of its last text change. An update keeps the number and the letter, bumps the version and moves changed in the same prrdgrep edit; created never moves. A duplicate touches nothing: no stamp, no source line, no version change.
- Existing G1 to G14 have no stamps: an EHT card backfills them from git (commit time is an upper bound on authoring time): G1 to G7 created and changed 2026-11-03T01:42:30+0100 (fdab237); G8 and G9 created 2026-11-03T01:42:30+0100, changed 2026-11-03T01:58:17+0100 (20cc824, their .2 versions); G10 to G14 created and changed 2026-11-03T20:02:09+0100 (8e61f7f). They are golden, so the backfill needs the owner approval. Until then the mod treats a rule with no stamp line as created and changed unknown, and adds a stamp line only to the rules it writes.

### 6. Writing the PRRD

- Writes go through prrdgrep, never by hand: $.process.run([prrdgrep, --design-dir, <root>/design, edit, ...], { env: { AIM_PILLAR_ALLOW_WRITE: "1" }, timeoutMs: 30000 }) (api chapter:278, 290; types:3648, ProcessRunInit carries cwd, env, stdin, timeoutMs, so the write gate is lifted for that one call only, never for the session). The mod never passes --user to prrdgrep: that flag acts as the owner, and only the owner may give it. Whether an edit of a golden rule needs --user is step 5 of ONYAD975, measured before any write path (increment I7) is built; the result goes to the owner with Q3 and Q16.
- New rule: one prrdgrep edit, a single all-or-nothing batch, anchored on the last non-blank line of the last rule of the tier section, replacing that line with itself plus the new block (declaration, stamp line, source lines). This is the edit-based insert that added G10 to G14 (8e61f7f), and it is atomic, unlike add followed by an edit. The number is the next free number over both tiers (numbers are never reused, edit-guard.ts:219-228 refuses a second declaration); a refusal because another writer took the number re-reads the PRRD and retries with the next number once, then fails loudly.
- Update of rule N: one edit batch that replaces the declaration line (version +1, new text) and the stamp line (changed only). The gate refuses a text change without a version bump, which enforces the rule.
- Sources (provisional on Q17): under the stamp line, one sub-bullet per span, "  - source: \"<span>\" (draft <draft id>)", quoting the redacted span; an update appends its new spans and keeps the old ones.
- After every write the mod runs prrdgrep lint on the corpus; a non-zero exit is logged and toasted (the write itself is already all-or-nothing).
- Which PRRD: <$.session.root()>/design/requirements/PRRD.md of the session that marked the message. If it is absent, or prrdgrep is not installed, or prrdgrep add would refuse an empty corpus (cli.ts:388: "no PRRD records ... refusing to guess"), nothing is written, the draft stays, and the toast says why. The mod never creates a PRRD (open question Q2).
- Tier: open question Q3, not settled here. The setting tier (golden or silver) exists, and its default is the answer the owner gives to Q3. Golden rules are set by the owner alone (USER rule prrd-design-rules), so no write path (increment I7) is built before the owner answers Q3 and Q16. The worked example below writes G rules only to show the numbers; the letter there is provisional on Q3.
- Section: the end of the tier section, before the next "## " heading or "---" divider, the same boundary prrdgrep add uses (cli.ts, the add case). In the 14-rule PRRD that is after G14.1 and before "## Approval and implementation status".
- Definitions: properties, attributes and measures definitions go into the PRRD as rules of kind properties or measures (directive 2 says "before adding it to the prrd.md"); design/specs/ is the rejected alternative. The kind is logged; the rule text carries no fixed prefix, and a measures definition has no required unit or range field.

### 7. Direct (directive 1)

No review step: the rules are added directly (directive 1, "they should directly be added"). A confirm toast with an undo command for golden writes is one of the options of Q3, built only if the owner picks it.

### 8. Switches, settings, debug log (G13, G14)

- Switches (G13, each on and off at runtime, remembered across sessions in $.store like the existing one, register.ts:261-316): save (the existing switch), extract, classify, add-to-prrd. Off extract: drafts only, as today. Off classify: candidates are only logged, never written (writing unclassified rules would add duplicates). Off add-to-prrd: candidates and labels are logged, the PRRD is not touched. Default: all on once the NPT cards and the eval card B1FEQVMM pass and the live check is done (Q11); until then extract ships off. The mechanism is the one of card 5IK59SQ2.
- Settings: extractModel and mergeModel (userConfig strings, default haiku, as jr-polish), openrouterApiKey and typesafeApiKey (sensitive, each sent only to its own provider), jevProvider (openrouter or typesafe), jevModel, dupThreshold, versionThreshold, jevConcurrency, contextMessages, promptBudgetChars, maxRuleChars, tier (its default is the owner answer to Q3).
- Debug log (G14, mechanism of card RWD5PW76): one line per step: context size and messages left out, candidate count, each rejected span with its reason, each Jev score as rule number and probability, each write with the prrdgrep exit code, each failure with its kind. Only redacted text and ids are logged, never the key and never a raw model reply.

### 9. Failure handling and valid state

Every failure leaves the PRRD as it was (each write is one prrdgrep batch) and the draft saved; the toast names the step. No retries except the single number-collision retry. The background job holds no lock beyond the prrdgrep document lock.

## Tests that can fail (directive list item 10)

Unit tests stub what the testing chapter says a test never runs (testing chapter:65-67, "No model, store, or tool runs in a test"). Each stub has its reason, and what a stub cannot show is measured by a card that calls the real thing:
- $.model.complete is stubbed because no model runs in a unit test: the tests check only what the code does with a reply (span check, order, rejection, the merge text check). Whether the real model finds buried, compound and code-embedded rules is measured by the eval card B1FEQVMM.
- Jev ($.http.fetch) is stubbed because the tests check the request bodies, the key isolation and the labels the code derives from given scores; whether real Jev scores the owner pairs as the design needs is measured by the calibration card 9J5JFR5V.

Each test names the line it guards.
- T1 buried (stubbed reply): a 4,000-character message of small talk and code with one requirement sentence in the middle, and a reply citing that sentence: one candidate, its span found; a reply whose span is not in the text is rejected (span rule provisional on Q19).

## OPEN QUESTIONS for the owner (a recommendation, where one is given, is not a decision)

- Q1 Context reading. Directive 5 can mean the 2 or 3 most recently MARKED messages, sorted by conversation order (this design), or the marked messages that come just BEFORE the new one in the conversation. Recommended: the first, because a rule split across messages marked out of order (the example marks 4 before 1) is found only that way.
- Q2 No PRRD in the project. Dev main has none, and prrdgrep refuses to add to an empty corpus. Recommended: never create one; save the draft and toast "no PRRD in this project"; a separate command to create a PRRD skeleton can be a later card.
- Q3 Tier. Golden rules are set by the owner alone, so the owner rules on the tier of every rule the pipeline writes; no option is the default. Options and trade-offs: (a) golden: the text comes from the owner own message and the owner act of marking it, and G1 to G14 are golden; but model-refined text then enters the golden tier unread, only the owner may fix it later, and if step 5 of ONYAD975 shows that a golden edit needs --user, the pipeline cannot write golden rules at all, because it never passes --user. (b) silver: model-refined text stays out of the golden tier and can be corrected without the owner; but an owner requirement lands in the lower tier and needs a promotion to become golden. (c) golden with a confirm toast and an undo command for each golden write: the owner sees each rule as it lands; but it adds a step the owner meets on every write, while directive 1 asks for a direct add, so it is built only if the owner picks it.
- Q4 Stamp placement. Recommended: a plain sub-bullet under the declaration ("  - created ... · changed ..."), so the backfill of G1 to G14 bumps no version. Alternative: on the declaration line, which forces fourteen version bumps and changes every pinned citation. The PRRD format rule (USER rule prrd-design-rules, "one flat bullet list per section") does not mention sub-bullets: the owner decides whether a sub-bullet for the stamps is allowed (the source sub-bullets are Q17), and the rule text is updated by the owner.
- Q5 Jev and privacy. The PRRD rules and the redacted candidates go to the Jev provider (OpenRouter or TypeSafe), a third party beyond the session provider. Recommended: accept, with the classify switch to turn it off; never send unredacted text.
- Q6 Jev key. Recommended: two sensitive userConfig options, openrouterApiKey and typesafeApiKey, each falling back only to the environment variables of its own provider (OPENROUTER_API_KEY; JEV_API_KEY or TYPESAFE_API_KEY) and each sent only to its own provider (point 4); without a key for the chosen provider, nothing is written to the PRRD and the toast says why.
- Q7 Thresholds and long rules. Recommended: dupThreshold 0.85 and versionThreshold 0.8 as placeholders, replaced by the values the calibration card measures (5 repeats; the Jev note found a run-to-run spread up to 0.09). G8.2 and G9.2 are long compound paragraphs on which Jev is expected to score worse; splitting them is a golden change the owner may want later.
- Q8 Middle band. Directive 12 says a candidate Jev matches in neither pass is new; this design applies it also to a candidate scoring just under both thresholds (logged). Recommended: as written. Deviation: hold such a candidate and ask.
- Q9 Pair packing. Directive 10 asks one pair per call. Deviation offered, not built: one request with the candidate as state and up to K independent questions, one existing rule each (Jev answers each question independently), which pays the candidate once instead of K times. Recommended: one pair per call first, packing only if the calibration shows equal scores.
- Q10 Models. Recommended: haiku for extraction and merge (jr-polish uses haiku; cost), with the userConfig options to pick sonnet if extraction quality is too low in the eval.
- Q11 Extract default. Recommended: the extract switch ships off until the NPT cards pass, the eval card B1FEQVMM passes and the live check is done, then on.

- Q12 Read together, directives 7 and 12 leave open where a candidate that is no rule at all is caught. Ask the owner whether they conflict or whether "no rule" is decided before the checks. Directive 7 lists "simply no rule at all" as an outcome of the classifier check; directive 12 says that a candidate neither check matches is added as a new rule, so with only the duplicate and version checks a candidate that is no rule would become a new rule. Settled either way: Haiku finds when a message holds no rule and returns no candidate for it (directives 4 and 10). Open: a candidate that reaches the Jev checks and is no rule. Options: (A) no step in the checks: the Haiku filter at extraction (notRules) is the only one, and Jev never judges whether a candidate is a rule; (B) not-a-rule as a further outcome inside the checks; (C) a separate Jev step before the two checks, asking whether the candidate is a requirement at all. Recommended, not decided: (A), because Haiku reads the whole message and its context, which a no-rule decision needs, while a Jev pair call sees only the candidate and one rule; (C) if the eval card B1FEQVMM shows that Haiku lets instructions through. The design text uses (A) provisionally.
- Q13 Order of the checks, and a candidate that is a duplicate of rule A and a version of rule B at once. Recommended: step 0, then pass 1 over every rule, then pass 2 over every rule only if pass 1 marked nothing; a duplicate anywhere wins, because writing nothing is the safer outcome and the duplicate already holds the meaning. Alternative: run both passes over all rules and pick the higher score.
- Q14 Numbers are never reused, deleted ones included. The PRRD file alone does not show deleted numbers, and prrdgrep add computes the next number from the current records only (cli.ts:389-395), so it can reuse a deleted top number. Recommended: the mod takes the next number above the maximum of the current records and of every number found in the git history of PRRD.md (git log -p over that one file, through $.process.run); outside git it uses the current file and logs that deleted numbers could not be checked. The same gap in prrdgrep add is reported upstream by the prrdgrep NPT card.
- Q15 Two readings of directive 13, to confirm (the design text follows them, provisionally). (a) The duplicate pass judges meaning, not wording: "make the background color of the loading dialog of a shade of blue" duplicates "the loading screen background should be blue" in other words, so the pass 1 question asks whether the candidate requires the same thing whatever the wording. (b) The version pass matches the element a rule governs, not the same claim: "must not be transparent" is a previous version of a rule about the same background, though it states another property, so pass 2 uses the labels same-element-adds, same-element-changes, same-element-removes and different-element. Trade-offs: (a) keeps one rule per element but changes owner text the owner has not read; (b) leaves the PRRD as the owner wrote it but drops the requirement until the owner acts; (c) keeps the requirement but adds a near-duplicate beside the owner rule. If Q3 picks golden, the same question holds for the golden rules the pipeline wrote itself. The pipeline never passes prrdgrep --user on its own; whether prrdgrep lets an edit of a golden rule through without it is step 5 of ONYAD975, measured before any write path is built. Options: (a) as designed: every rule shows the owner words it came from, typos included; (b) only the draft id, with no quoted text; (c) no source lines: the spans stay in the draft and the debug log only.
