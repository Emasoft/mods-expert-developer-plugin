# The agent loads chapter skills at runtime instead of preloading 28 of them

THE OWNER'S DECISION (2026-10-20): the agent should load the skill it wants, on demand. The skills-menu exists for exactly that, so the preload roster is no longer a product call - it is a consequence of the routing design.

THE CHANGE. The agent's `skills:` frontmatter keeps only the four tool skills (tldr-code, fastedit, jgrep, quicksilver), which the agent needs on nearly every run. The 60 documentation chapters move OUT of the preload window and stay in the `skills:` list as a tail, so they remain declared and reachable but their content is no longer injected at startup. The agent's own 'Chapter skill index' table is the routing aid it uses to pick one.

THE MEASUREMENT. The 32 preloaded entries carry 63143 bytes of local SKILL.md content - about 15.8k tokens injected into EVERY invocation of the agent. The four tool skills are user-scope plugins, not local files, so the 63143 bytes is entirely the 28 documentation wrappers. A router agent that loads ONE chapter per task is paying for 28 it did not choose.

WHY RUNTIME IS THE CORRECT PATTERN AND NOT A TRADEOFF. The sub-agents documentation says the `skills:` field controls what is PRELOADED, not what is ACCESSIBLE: a skill past the window is still discoverable and invocable through the Skill tool during execution. A runtime load lands in the MESSAGE TAIL and cannot invalidate the cached prefix; a preload injects full content into EVERY invocation, so the 'fix' of moving runtime loads into the frontmatter is strictly worse for a sometimes-needed skill and worse always for a router agent.

THE INVOCABILITY FACT THIS DEPENDS ON, VERIFIED AGAINST THE DOCUMENTATION AND NOT ASSUMED. All 60 documentation skills declare `user-invocable: false`, which per the skills documentation prevents the HUMAN from typing /name and does NOT prevent Claude from invoking the skill ('Only Claude can invoke the skill'). None of them declares `disable-model-invocation: true`, which is the key that WOULD make a preload inert and would also block runtime invocation. The agent declares no `tools:` or `disallowedTools:` field, so it inherits the Skill tool. Therefore: a chapter outside the preload window is still invocable by the agent at runtime.

WHAT MUST CHANGE TOGETHER, because four artifacts describe the same 60 skills and the tests pin their agreement: (1) the agent's `skills:` frontmatter - the 56 chapter entries after the four tool skills move out of the first 32 positions; (2) `PINNED_PRELOAD_SKILLS` in tests/test_skills_menu.py - the mirror of the window, which becomes the four tool skills; (3) the agent body's 'Chapter skill index' table - its prose must say the chapters are loaded on demand rather than preloaded; (4) README.md - its Components/preload description says the same. DELEGATION.md's skills-menu bullet also states the preload design and must be corrected.

THE TEST THAT MUST CHANGE WITH THE DESIGN, NOT AFTER IT. test_preload_window_is_exactly_the_pinned_roster pins the window to a set. The window is now exactly the four tool skills, and the property that matters is not 'which 32' but 'no documentation chapter is preloaded, and every chapter is still declared'. A new test should assert that the preload window contains no documentation chapter, and that all 60 remain in the `skills:` list - so a future edit that re-injects a chapter into the window fails a test rather than silently costing 15.8k tokens per invocation.

WHY THE INDEX TABLE BECOMES LOAD-BEARING RATHER THAN DECORATIVE. The table currently documents the routing order for a reader. After this change it is the agent's actual route to a chapter, so a stale row stops being a documentation defect and becomes a routing defect. The test that already pins the table to the frontmatter and to each skill's H1 heading therefore becomes more important, not less.

WHAT THIS DOES NOT CHANGE. The chapters still ship, still are reachable, and still carry the same content. The README catalogue still lists all 60. The guard-coverage work and the consent registry are untouched by this decision.

## THE MEASUREMENT PROVENANCE FOR THE BYTE FIGURES

THREE BYTE FIGURES APPEAR ON THIS CARD - 63143, 72071 and 140916 - AND THEY ARE NOT THE SAME MEASUREMENT. 63143 bytes is the ORIGINAL WINDOW'S DOCUMENTATION PORTION, the state before the four tool skills were removed: that window was 32 NAMES WIDE - the four user-scope tool skills first, then the first 28 DOCUMENTATION chapters - but the tool skills are not shipped by this plugin, so they contribute no local bytes at all, and the 63143 is entirely the 28 chapters' SKILL.md bytes. So 63143 measures 28 CHAPTERS, not a 28-skill window, and the distinction matters for reading the next figure. 72071 bytes is the CURRENT 32-SKILL WINDOW, the first 32 declared names in the shipped frontmatter, all 32 of them documentation chapters. The 60 chapters together are 140916 bytes, which is NOT what gets injected: the preload window is 32 names, not 60. So the cost of the shipped configuration is 72071 bytes, about 18k tokens, an approximation from the byte count, per invocation - and it is paid for 32 chapters, not for all 60. The step from 63143 to 72071 is itself accounted for: 72071 minus 63143 is 8928 bytes, which is the four chapters that entered the window when the four tool skills left it.
THE MEASUREMENT, RE-RUN AND RE-DERIVED ON 2026-10-20, so a reader can re-check it: the 60 chapter names are read from the `skills:` frontmatter of agents/mods-expert-developer-agent.md, and for each name the bytes of skills/<name>/SKILL.md are summed. All 60 resolve to a shipped SKILL.md, so the sum is over 60 real files and no name contributes zero. The sums are 72071 for the first 32, 140916 for all 60, and 63143 for the first 28 - the last being the pre-removal window, which is why the card's own earlier section quotes it.
THE PRECISE CLAIM THE 72071 NUMBER MAKES, so it is not read as more than it is: it is the summed byte size of the 32 SKILL.md files whose NAMES occupy the first 32 positions of the agent's `skills:` frontmatter. It is a measure of CONTENT ON DISK, not of tokens actually injected: the harness injects the content of the preloaded skills, and the byte-to-token conversion is the card's approximation, not a measured token count. The approximation is a DIVIDE BY FOUR, and it is stated so a reader can re-derive the token figures: 72071 divided by 4 is 18017.75, which rounds to 18018 and is written as 'about 18k tokens'; 63143 divided by 4 is 15785.75, which rounds to 15786 and is the card's earlier 'about 15.8k tokens'; and the 4608-byte saving in the next paragraph divided by 4 is 1152 EXACTLY, written as 'about 1.2k tokens'. No token count in this section was measured by a tokenizer; every one of them is the byte figure divided by four, and a reader who prefers a different ratio can apply it to the same byte figures.
WHAT THE DECISION IN BOX 7 IS ACTUALLY ABOUT, stated so the byte figures cannot be confused with it. THE HARNESS RULE IS ONE SENTENCE, and the card cites it as one: 'the full content of each listed skill is injected into the subagent's context at startup, up to the first 32 distinct names in the list' (skills/mods-doc-subagents-reference/references/chapter.md, line 626) - the sentence states WHAT IS INJECTED - the full content of each listed skill - WHEN - into the subagent's context at startup - and HOW MANY - it is limited to the first 32 distinct names in the list - and it is that LIMIT that fixes the window's membership. So the window's SIZE is min(32, the number of distinct declared names) and its MEMBERSHIP is the first 32 distinct names - which, for a list that repeats a name, reaches PAST position 32, because a repeated name does not consume a second slot. The shipped frontmatter has no duplicate names (test_preloaded_skills_are_the_first_entries_in_frontmatter_order asserts the window itself is duplicate-free), so here 'the first 32 distinct names' and 'the first 32 names' select the same set. Three consequences, stated separately so that none is read as a sub-case of another. FIRST, declaring MORE chapters does not raise the cost, because the window is capped at 32 either way. SECOND, declaring FEWER than 32 distinct names is the only way to lower the cost by declaring fewer. THIRD, REORDERING so that smaller chapters sit inside the window lowers the cost too, and it is priced in the next paragraph, because it is not free. THE PREMISE OF THAT THIRD CONSEQUENCE IS ITSELF UNVERIFIED, and the card says so rather than let the lever read as available: DELEGATION.md records that the documentation gives order WITHIN the window no meaning - 'an argument from silence, not a documented guarantee' - and that only reordering the frontmatter's TAIL is free. What the documentation states is that the first 32 NAMES are preloaded; it does not state that the order of those names is a routing order, so whether a size sort is a legitimate way to choose them is the owner's judgement about the artifact, not a harness guarantee. Leaving the chapters UNDECLARED removes them from the window entirely, at a cost of zero. So the decision is whether the 32 chapters in the window are worth 72071 bytes, not whether 60 are.
THE COST OF THE REORDER LEVER, because a lever stated without its price reads as free - and because a lever whose PREMISE is unverified, as the previous paragraph records, must not be priced as though it were available. Reordering the frontmatter to put the 32 SMALLEST chapters first would take the window from 72071 bytes to 67463, a saving of 4608 bytes - 6.4% of the window, and about 1.2k tokens at the divide-by-four ratio stated above. The reorder does not change the NUMBER of chapters in the window, only their IDENTITY, and that is what makes it a lever at all. THAT SAVING IS NOT FREE, in two ways, and both are measurable. FIRST, the reorder is not a one-line edit: test_frontmatter_and_body_index_list_the_same_skills_in_the_same_order requires the agent body's Chapter skill index table to be reordered in step with the frontmatter, because the body table is the human-facing copy of the routing order - so the routing order a reader sees would be scrambled by chapter size, which is a cost in the artifact's own terms, not a matter of taste. SECOND, and more consequentially, the 4608 bytes buy a DIFFERENT ROSTER: 13 of the 32 currently curated chapters would LEAVE the window, among them mods-doc-mods-overview, mods-doc-mods-troubleshooting, mods-doc-mods-reference, mods-doc-plugins-security-and-trust and mods-doc-plugin-manifest-reference, and 13 chapters currently in the tail would ENTER it, among them mods-doc-headless-mode-reference and mods-doc-cc-debug-mode. A router that wants ONE chapter is most likely to want one of the ones a size sort would drop. Whether the routing order is a product decision the owner makes by hand, or a consequence of chapter size, is the owner's call, and this card does not make it.
THE BOX 7 NUMBER IS RESTATED TO MATCH THIS MEASUREMENT, so the reader of box 7 and the reader of this section carry the same figure: the cost is 72071 bytes - about 18k tokens, an approximation from the byte count, at the divide-by-four ratio stated above - of content injected into every invocation of a router agent that typically wants one chapter, and the card's earlier 63143 figure is the pre-removal window's 28 documentation chapters, a different measurement of a different configuration.
WHAT THE 72071 FIGURE DOES NOT INCLUDE, so the cost is not over-stated, and the size of the gap is stated so that the reader judges the lower bound with its magnitude in view. It is the SKILL.md bytes of the 32 chapters in the window, and of nothing else. It EXCLUDES the reference files, the catalogue, and the per-skill directory overhead, and the exclusion of the reference files is an ASSUMPTION, not a measurement: nothing in this repository states whether a skill's auxiliary files are part of the 'full content' the harness injects, and the shipped sub-agents chapter says 'the full content of each listed skill is injected' (skills/mods-doc-subagents-reference/references/chapter.md, line 626) without saying whether 'full content' means the SKILL.md alone or the skill's whole directory. THE EXCLUDED PART IS NOT NEGLIGIBLE: the same 32 chapters carry 1355771 bytes of non-SKILL.md files, almost all of it references/chapter.md, against the 72071 bytes of SKILL.md - 18.8 times the measured figure. THAT FIGURE COUNTS GIT-TRACKED FILES ONLY, and the qualifier matters: a plain walk of the same 32 directories also picks up 196736 bytes of untracked macOS .DS_Store metadata, which a clean checkout does not have, so the figure a reader reproduces from a clone is the one stated here. The 72071 figure is therefore a LOWER BOUND on what the preloaded chapters carry, and the gap is LARGE: the tracked on-disk total of those 32 chapters is 1427842 bytes - 19.8 times the measured figure - and whether the harness injects each chapter's SKILL.md ALONE or its WHOLE DIRECTORY is NOT YET MEASURED, because the shipped rule says 'the full content of each listed skill' and nothing in this repository says which of the two that is.
