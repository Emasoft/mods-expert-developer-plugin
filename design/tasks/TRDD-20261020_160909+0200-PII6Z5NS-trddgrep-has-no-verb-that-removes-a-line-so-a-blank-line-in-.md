# trddgrep has no verb that removes a line, so a blank line in an existing card cannot be removed in place and the strict scan blocks on it

THE DEFECT, AS OF UPSTREAM HEAD. trddgrep edit replaces TEXT WITHIN a line (lib/pillar/edit.ts PASS 2: lines[line-1] = before.replace(expect, () => replace)), so a line disappears only when its whole text is replaced by the empty string. A BLANK line has no text, so --expect can never match it, and three separate guards each refuse the attempt: an empty --expect is refused outright (a comparand that matches every string is not a compare-and-swap); a whitespace comparand fails the staleness check, because the line does not contain a space; and trddgrep fix has no whitespace repair, because MD012 is markdownlint's rule and not a trddgrep lint finding. The file's blank run is SEVERAL separate array elements (splitLines splits on every newline), and an element can only be edited if expect matches text it contains. THE CONSEQUENCE, FOR THE RELEASED TOOL: a card that acquires two or more consecutive blank lines CANNOT BE REPAIRED WITH ANY VERB, and the strict scan reports each one as an MD012 NIT, so the release is blocked by a defect no verb can fix. THE SCOPE OF THAT CLAIM, stated up front because a later section of this card shows it is no longer true of the tool installed on this machine: everything in this paragraph describes UPSTREAM HEAD. The paragraph beginning 'THE TOOL STATE THIS CARD DESCRIBES' below, in the section 'THE SAME TOOL PATH, THE OTHER WAY: A PREFIX --expect SPLICES TWO VERSIONS OF ONE LINE', records a WORKING remedy for the blank comparand in the installed tool's own working tree, so a reader with that tool must read the two together and not the first alone. THE PLAIN ANSWER TO THE QUESTION THIS CARD'S TITLE ASKS, stated here so a reader does not have to reach the fifth body paragraph to get it: WITH THE TOOL INSTALLED ON THIS MACHINE, a blank line CAN be removed - 'trddgrep edit --at-line N --expect-blank --replace "" --allow-empty-replace' deletes the line outright - and WITH UPSTREAM HEAD, it cannot, because no released verb addresses a line that carries no content. The card's title says 'no verb that removes a line', and that is true of the RELEASED tool; this paragraph is the scope of that claim, and the PARAGRAPH - a paragraph, not a heading - that begins 'THE TOOL STATE THIS CARD DESCRIBES', which is BELOW this one records the working remedy and the date it was measured. THIS PARAGRAPH IS TRUE AS OF 2026-10-20 against the install root's working tree, and it must be RE-VERIFIED when that tree changes, because the implementation it describes is uncommitted upstream and can be committed, reverted, or changed without notice - and no test in this repository watches it.

THE INSTANCE IN THIS REPOSITORY. design/tasks/TRDD-20261020_143209+0200-07W10I9D-*.md carries five consecutive blank lines and three consecutive blank lines. They were introduced by commit 4c2c80a, which removed three paragraphs the section restructure had left duplicated, using trddgrep edit --replace "" --allow-empty-replace. That verb emptied the duplicated paragraphs' TEXT but left the blank lines that surrounded them, and the two runs are the residue. The card is otherwise correct: each heading owns its paragraph, and the paragraphs appear exactly once.

WHAT WAS TRIED, so the next reader does not repeat it. An empty --expect is refused by design. A single-space --expect is refused by the staleness check. trddgrep fix repairs nothing here. trddgrep append backs over a section's TRAILING blank run before inserting, but it only INSERTS - the blanks it backs over remain after the inserted line, so the count does not change (measured). A multi-line --replace INSERTS newlines into one element, which adds physical lines but never removes an element, and the array size is invariant. A multi-line --expect can only match an element that ALREADY holds newlines, and the only way to give it newlines is a previous multi-line --replace, so the two-call sequence does not help either. Emptied elements become blank elements, so emptying a content line ADDS a blank. The blank-run LENGTH IS THEREFORE INVARIANT under every available verb, and the run of five cannot be reduced to one.

THE UPSTREAM HALF IS FILED as Emasoft/ai-maestro#183, with the three refusals quoted and the invariant argued. The remedy it asks for is a verb or flag that removes a line rather than replacing its text - for example trddgrep edit --at-line N --delete-line, or a spelling for an explicitly blank comparand that is not the empty string, so the compare-and-swap guard is not defeated. check-box already addresses a line by ORDINAL rather than by content, which is the same idea: a line is a position, and a position can be deleted.
THE TOOL STATE THIS CARD DESCRIBES, and the day it was MEASURED, because the card's claim is now about a RELEASED tool and not about the tool on every machine. (The card names no day on which the claim stopped being true, and it cannot: the implementation is UNCOMMITTED upstream, so it can be committed, reverted or changed without notice, and no day can be named for a change nobody has made.) The claim above - that no verb can delete a line - is TRUE OF UPSTREAM HEAD, and it is FALSE of the trddgrep INSTALLED on this machine on 2026-10-20, and THIS paragraph records it - the verb, the command and the measurement are all in it. THE INSTALLED TOOL ALREADY HAS THE VERB, and this was verified by RUNNING it, not by reading its help: the installed trddgrep resolves through the launcher to the ai-maestro install root, and that install root's WORKING TREE carries an UNCOMMITTED implementation of the blank comparand - '--expect-blank', which names a comparand whose predicate is that the line carries NO CONTENT, and whose empty --replace DELETES the line, leaving the document shorter. Measured on a scratch corpus: a card with a blank line at line 23 was edited with 'trddgrep edit <id> --at-line 23 --expect-blank --replace "" --allow-empty-replace', and the result was that the blank line was GONE - the file was one line shorter, not a line left empty. So the remedy for #183 EXISTS, is WORKING, and is NOT YET RELEASED: 'git show HEAD:lib/pillar/edit.ts' at the install root contains no occurrence of expectBlank, and the working tree contains six. Issue #183 is still OPEN upstream. WHAT THIS DOES TO THE CARD. The invariant argued above - that a blank line cannot be removed, so a blank-run's length cannot be reduced - is a true statement about upstream HEAD and a false statement about the tool a session on this machine would actually run, so a reader who tries the card's conclusion with the installed CLI will find a verb where the card says there is none. The card's own claim is therefore SCOPED TO UPSTREAM HEAD, and the working-tree implementation is recorded here so that the next session does not have to rediscover it. The two halves of that scope are not in conflict with the repair recorded in this card's Approval log: the repair of the instance used a git revert plus three full-line edits, and it did not need the blank comparand, because the surplus blank lines were the residue of three deleted paragraphs and restoring the paragraphs' CONTENT put the content back where the blanks had been. The verb would have removed the blanks directly.

WHY THIS MATTERS BEYOND ONE FILE. The strict scan collects every gitignore-visible markdown file, so a defect in ANY card in the corpus blocks the release, and the tool that governs the cards is the tool that cannot repair it. THE INVARIANT IS NARROWER THAN 'A CARD CANNOT BE REPAIRED', AND THE DIFFERENCE MATTERS. What is proven is that a BLANK LINE CANNOT BE REMOVED IN PLACE - no verb can delete a line from an existing card. A card can still be REBUILT: trddgrep new --body writes a card with an arbitrary multi-line body, and the body of this very card was written that way, with no blank-line run. The obstacle to that route is not the tool but the OLD FILE: rebuilding produces a second card, and the original stays in the corpus, where the scan still lints it. So the two routes are (a) the missing verb, which repairs a card in place, and (b) rebuild plus retire the old file, which needs the old file to leave the tree rather than be archived - and the corpus has no verb that removes a card file. A card that acquires a blank line from an ordinary edit is therefore unrepairable IN PLACE until the missing verb ships, and only in place.

## THE SAME TOOL PATH, THE OTHER WAY: A PREFIX --expect SPLICES TWO VERSIONS OF ONE LINE

THIS SECTION RECORDS A SECOND DEFECT OF THE SAME LINE-ADDRESSED WRITE, and it is a DIFFERENT SUBJECT from this card's own: this card is about a line that cannot be REMOVED, and this section is about a line that can be replaced only PARTIALLY. The two are separate propositions about the same function, and this section is here because the card that asserts this defect is ARCHIVED and cannot take a write - not because the subjects are one. The blank-line invariant above says a line can only be REPLACED, never deleted; the consequence THIS SECTION records is that a PREFIX replacement does not replace the LINE either - it replaces a PREFIX of the line and leaves the rest of that line in place, so the line ends up carrying TWO VERSIONS OF ITSELF. A reader who came here for the blank-line question can skip this section; the defect it records is asserted in full on the archived card TRDD-QARM420U.
THE PROOF, IN TWO COMPLEMENTARY PIECES, because neither alone would be airtight. The diff alone shows the SHAPE; the source alone shows the CAPABILITY; only together do they close. PIECE ONE, THE SHAPE: commit 17fe628 - this repository's own earlier repair of the affected card - replaced one Approval-log line with a line of 2717 characters where the pre-image line was 1346, and the post-image RETAINS THE PRE-IMAGE'S TAIL. The decomposition is exact and re-derivable, and it is given here in full so that a reader can check it rather than trust it: the pre-image line was 1346 characters; the --expect matched its FIRST 200 characters, ending mid-word at 'ile content changed)'; the replacement text was 1571 characters; the apply left the pre-image's remaining 1146 characters in place, and 1571 plus 1146 is 2717. The 200-character boundary is not a guess but a derivation. The WEAKER identity - that the post-image ENDS with the pre-image's remainder - is under-determined: it holds for 1146 of the 1347 boundaries of that 1346-character line - the 1146 whose remainder is NON-EMPTY; the 1347th leaves an empty remainder, which every string ends with, so the identity holds there only VACUOUSLY - and a reader who tries only that test will find the split ambiguous. The DETERMINED form is the direction the tail runs: the spliced tail must BEGIN at the mid-word seam, not merely end with the pre-image, and of the 1347 boundaries of the line exactly ONE makes the pre-image's remainder START at that seam. So the --expect was 200 characters and the replacement was 1571. PIECE TWO, THE CAPABILITY: lib/pillar/edit.ts validates an edit with 'actual.includes(e.expect)' and then applies 'before.replace(e.expect, () => e.replace)', and String.prototype.replace with a string pattern replaces the FIRST occurrence and leaves the remainder of the line in place.
SO A --expect THAT IS A PREFIX OF A LONG LINE DOES NOT REPLACE THE LINE, IT SPLICES: the replacement text is written where the prefix was, and the old line's TAIL follows it. The result is a well-formed line in a well-formed card that reads as coherent prose on every read, because both halves are individually coherent text about the same subject - and the two halves can CONTRADICT each other, which is what makes the damage silent rather than obvious.
WHY THE WRITE GATE DOES NOT NOTICE. The staleness check asks only whether the expected text is PRESENT on the named line, which a prefix satisfies, and the apply replaces the first occurrence, which is exactly the prefix. A gate that compared the RESULT against the line the caller believed it was replacing would catch it, and a length check would catch it in this instance, where the splice grew the line from 1346 to 2717 characters. Neither exists, and a card edit that produces a longer line than the one it replaced is not an error the tool reports. The length check is a HEURISTIC FOR THIS SHAPE, not a general detector, and it is named as such so it is not mistaken for one: a prefix edit whose replacement is LONGER than the pre-image's remainder also grows the line, and so does a legitimate full-line replacement that happens to be longer. Only the comparison against the caller's intended line distinguishes them, and the tool has no way to state that intent.
THE DAMAGE IS PERMANENT WHERE IT LANDS, and the reason is a property of THE SPLICED LINE, not of the tool's vocabulary. THE AFFECTED CARD IS ARCHIVED, and an archived card is refused by two SEPARATE guards: the APPEND path, lib/trdd-store.ts, refuses an append with the comment 'an archived card takes no append at all - not even to ## Approval log' (the archived-zone check precedes the Approval-log exemption), and the EDIT path, lib/pillar/edit-guard.ts, refuses a raw line edit of an archived card. But the EDIT path is NOT ABSOLUTE, and this card must say so: upstream issue Emasoft/ai-maestro#179 carries a NARROW EXCEPTION, present in the installed tree (commit b0a714591, on the install root's branch governance-rules), under which exactly ONE changed body line that FALSELY and MACHINE-VERIFIABLY contradicts the card's own column MAY be corrected in an archived card. THE SPLICED LINE DOES NOT QUALIFY, and that is why the damage is permanent: it carries no pipeline-state claim about the card's own column, so the exception's predicate is false of it. That, and not the absence of a verb, is why the correction for this defect had to be recorded on a LIVE card instead of on the card it describes. THE ARCHIVED CARD TRDD-QARM420U STATES THAT SAME REASON, and the sentence this paragraph replaces pointed at the tool's vocabulary instead - the wrong category, and wrong about the tool as well, since the vocabulary now contains a narrow verb for this shape of repair.
THE UPSTREAM HALF IS FILED as Emasoft/ai-maestro#184, which asks for a verb that replaces a WHOLE LINE, or a guard that refuses a --expect which is only a PREFIX of the line it names. The two issues share a ROOT CAUSE - a line can only be addressed by its CONTENT, and no verb addresses it as a unit - but their remedies as filed are not the same flag: #183 asks for a verb that REMOVES a line, and #184 asks EITHER for a verb that replaces a WHOLE LINE or for a guard that refuses a --expect which is only a PREFIX of the line it names. A --whole-line verb would serve both; a --delete-line verb would serve #183 but would not, by itself, stop a prefix splice.
THE READING DISCIPLINE THIS PROVES, which is the part a future session can act on: the corruption was caught only because the file was read WHOLE, after the fact, rather than skimmed, and only because the line's LENGTH was measured. A card can therefore be corrupted without any tool reporting it, and the only detector that works is reading the whole file. The line in the affected card that carried the damage was 2717 characters where it should have been 1571 - a length that is visible only if something measures it.
WHAT IS NOT CLAIMED HERE. The mechanism is shown for THIS instance, by the diff and by the source; it is not claimed that every prefix edit splices, nor that a reader can tell from a successful edit that a splice occurred. The remedy is upstream, and until it ships the detector is the discipline: read the whole file, and measure the length of a line you have just edited.
