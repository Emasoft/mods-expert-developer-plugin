# The release gate cannot tell a validator abort from a finding because the abort exits inside the verdict range

THE DEFECT. The release gate's validator step in scripts/publish.py (stage G3, the `ve = subprocess.run(...)` block) maps the validator's exit code to a verdict with a 0..4 vocabulary: 0 = pass, 1 = CRITICAL, 2 = MAJOR, 3 = MINOR, 4 = NIT, and >= 5 = "the validator FAILED TO RUN". The gate's own comment says the >= 5 branch exists so that "anything >= 5 is not a verdict at all - the validator FAILING TO RUN (127 = entrypoint missing, 137 = OOM-kill, ...)" and that the old `ve != 0 and ve < 5` test "let every one of those fall through and print 'Validation passed', which is the exact RC-8 fail-open the CI workflows were fixed for".

THE GAP. That reasoning assumes a 1..4 exit code always means a completed validation. It does not. CPV's GitHub-integrity check ABORTS the run before any validation happens, and the abort's exit code lands INSIDE the 1..4 range - the observed run exits 2, which this card does NOT claim is always 2 - so the gate labels the abort with the severity name of whatever code it happens to carry, and cannot tell an abort from a finding of that severity. The gate therefore blocks (exit 2 is in the blocking range), which is the safe outcome, but it PRINTS "BLOCKED: MAJOR issues found", a claim that is false: no finding exists, because nothing was validated. The gate's fail-closed property survives; its DIAGNOSIS does not.

MEASURED, 2026-10-21, in this repository at commit 6dd97b1, with the validator's OWN exit code and not a pipe's (the previous turn's reading of "exit 0" was the exit code of `tail` at the end of a pipe, not of the validator): the unbypassed invocation exits 2, prints the CPV integrity-error block, and produces NO "SUMMARY:" line. IN THE OBSERVED ABORT RUN the abort's text went to STDERR - 4480 bytes on stderr and 0 bytes on stdout - and this card does not claim that every abort run splits its streams the same way. The abort's own heading is "[CPV integrity] CRITICAL: integrity manifest mismatch". The same invocation with PLUGIN_SKIP_GITHUB_INTEGRITY=1 - the bypass the integrity error message itself prescribes - exits 0 and prints SUMMARY: CRITICAL=0 MAJOR=0 MINOR=0 NIT=0 WARNING=72 on STDOUT - exactly one SUMMARY line in 27430 bytes of stdout - while its 102 "[cpv-phase]" progress lines went to STDERR, 5057 bytes of stderr. THE COMPLETED RUN THEREFORE WRITES TO BOTH STREAMS, with the SUMMARY on stdout and the progress lines on stderr, and the gate, AS IT STANDS TODAY, captures NEITHER stream, so an abort is invisible to the gate as anything but an exit code.

WHY THIS IS ITS OWN CARD. It is a defect in the release gate, not in either of the two chapter-preload cards it was found while working on, and it is not a documentation defect at all: it is a wrong label on a release-blocking verdict. A reader of the gate's output is told a MAJOR finding exists when the true state is that the validator did not run, which sends the next person hunting for a MAJOR finding that is not there. It is also the SECOND instance of the same shape this project has already hit once - a validator outcome that cannot run is not a clean outcome - and the first instance (the MD012 blank-line NIT, tracked by TRDD-PII6Z5NS) is about the release gate's response to a finding rather than to an abort.

THE FIX, and it is small. The gate needs to distinguish "the validator ran and found something" from "the validator aborted". ONE REQUIREMENT, and it is the one the acceptance checklist below already requires: before a 0..4 exit code is accepted, the gate must establish that the validator PRODUCED A VERDICT, and it must establish that from a capture of BOTH STDOUT AND STDERR. TWO CHECKS FALL OUT OF THAT ONE REQUIREMENT, and both are needed. FIRST, the validator's SUMMARY line must be PRESENT, so an aborted run can never be read as a finding of any severity. SECOND, the abort's own heading must be ABSENT, so a run that aborted is refused with "BLOCKED: the validator could not run (integrity check aborted) - UNKNOWN is not clean" - the wording the >= 5 branch already uses for the same situation. A SINGLE-STREAM READ CANNOT SUPPLY BOTH CHECKS: a stderr-only read finds the abort's heading but never the SUMMARY, and a stdout-only read finds the SUMMARY but never the abort. The verdict this card names is the validator's SUMMARY line, and WHERE TO READ IT IS NOW MEASURED: in the completed run the SUMMARY line was on STDOUT - exactly one occurrence in 27430 bytes of stdout - and in the observed abort run the abort's heading was on STDERR - 4480 bytes of stderr and 0 bytes of stdout. IN THAT OBSERVED PAIR the two markers were on different streams, so a fix reading ONE stream saw only one of the two cases: reading stdout alone found the SUMMARY but not the abort, and reading stderr alone found the abort but not the SUMMARY. THAT IS WHAT SHAPES THE FIX, and the rule the requirement adopts is premise-free: it requires that the validator PRODUCED A VERDICT, and the mechanism that makes the requirement stream-agnostic is that the check is a SEARCH ACROSS WHATEVER WAS CAPTURED, wherever the verdict was carried - so the requirement names no stream and rests on nothing the observations above could contradict. INSPECTING BOTH CAPTURED STREAMS is the conservative implementation of that rule - the abort token is looked for in stderr AND stdout, and the SUMMARY precondition is looked for in stdout AND stderr - so the requirement depends on having CAPTURED BOTH STREAMS rather than on which one CPV chose to write to. THE OBSERVATIONS ABOVE SHOW that a single-stream read is insufficient, and they are scoped to the validator the gate pins in the argv it calls, v5.22.0, so they describe that version's output. THEY MUST BE RE-MEASURED on either of two independent triggers: the validator pin in the argv being lifted, which changes what this gate runs, OR a CPV release changing its own output formatting, which changes what that version emits and needs no change here. THE REQUIREMENT NEEDS A CAPTURE THAT THE GATE DOES NOT DO TODAY, and the review of this card is right that the original text here was wrong to call them sufficient as written: the call is `subprocess.run(["uvx", "--from", "git+https://github.com/Emasoft/claude-plugins-validation@v5.22.0", "--with", "pyyaml", "cpv-remote-validate", "plugin", ".", "--strict"], cwd=str(root), timeout=_CPV_TIMEOUT_SEC).returncode` with NO capture_output and NO stdout= or stderr= argument, so the validator's output is INHERITED by the parent process and streams to the console, and the gate has no string to inspect. A fix must first capture the output - `capture_output=True`, or equivalently `stdout=subprocess.PIPE` and `stderr=subprocess.PIPE` - and then RE-EMIT it, so the operator still sees the validator's own report; capturing it silently would hide the very evidence the operator needs. THE RE-EMIT MUST HAPPEN BEFORE THE GATE PRINTS ITS VERDICT, so the evidence sits above the conclusion rather than below it. The token to match is the abort's own heading, "[CPV integrity] CRITICAL: integrity manifest mismatch", which CPV prints verbatim; note that CPV itself calls the abort CRITICAL, so the gate's "MAJOR" label is not merely mislabelled but contradicts the tool's own severity. Match the heading, not the prose around it, which is CPV's error text and may change. THE HEADING IS CPV'S OWN STRING, not this repository's: it is the most stable token AVAILABLE, but it is not under this repository's control and can change with any CPV release, and a release that changes it must be caught by the test in the acceptance checklist below rather than silently turning the gate into a pass. The gate's fail-closed property must be preserved: the abort must still block, and must be reported as an abort.

THE UNRELATED DEFECT THIS IS NOT. The upstream CPV integrity failure itself (Emasoft/claude-plugins-validation issue #243) is not this card's subject and is not fixable here: it is a released-version problem in another repository. This card is about how THIS repository's gate RESPONDS to a validator that did not run, which is fixable here and matters independently of whether issue #243 is ever fixed.

## Acceptance checklist

- [ ] 1. The gate distinguishes a validator ABORT from a finding: a run whose output carries the abort heading is refused with a message that says the validator could not run, and NOT with the severity name of the exit code it happened to carry.
- [ ] 2. The capture does not hide the operator's evidence: the validator's stdout and stderr are re-emitted after capture, so the operator still sees the validator's own report - including the abort block - rather than an empty console. The re-emit happens BEFORE the gate prints its verdict, so the evidence appears above the conclusion rather than below it.
- [ ] 3. The gate's fail-closed property is preserved: the abort still BLOCKS the release. The defect being fixed is the MISLABEL, not the refusal - a fix that let the abort through would be a worse defect than the one this card records.
- [ ] 4. The match is on a STABLE token, not on the abort's prose: the abort's heading, not the error text around it, which belongs to CPV and may change. The token this card names is the heading CPV prints verbatim, and it is searched in BOTH captured streams, because the completed run's SUMMARY is on stdout and the observed abort's heading is on stderr. The token is CPV'S string, not this repository's: it is the most stable token AVAILABLE, and a CPV release that changes it must be caught by the test in box 5 rather than silently turning the gate into a pass.
- [ ] 5. A TEST covers the abort path, and it asserts the negative outcome: given a validator that exits inside the verdict range without producing a verdict, the gate REFUSES and says the validator could not run. A test that only exercises the passing path proves nothing about the defect this card records. The test also covers the two cases that would let a fix pass silently: a validator that exits 0 while carrying the abort token must NOT be read as a pass, and a captured abort with NO SUMMARY in EITHER stream must be REFUSED rather than accepted on the exit code alone. These two cases were added by adversarial review of this card rather than by the original defect report, and they are in service of the same fail-open concern.
