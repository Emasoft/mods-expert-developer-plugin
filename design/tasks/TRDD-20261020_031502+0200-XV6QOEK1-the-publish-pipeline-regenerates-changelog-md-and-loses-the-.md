# The publish pipeline regenerates CHANGELOG.md and loses the 0.1.0 section on a tagless repository

MEASURED, NOT HYPOTHETICAL. The repository has NO TAGS (git tag returns 0; git describe fails). scripts/publish.py:2741 stage_changelog runs: git cliff --bump --tag v<NEXT> -o CHANGELOG.md, and -o OVERWRITES the file.

REPRODUCED on a clone of this repository. Running the pipeline's exact command produces the file with the 0.1.0 section ABSENT: the rendered output contains no '0.1.0' heading and none of the 0.1.0-era prose, because --bump on a repository with no tags warns 'There is nothing to bump' and the file is written from the commit log alone, with no prior release to anchor it. The commits themselves survive in the render (their shas appear), but the 0.1.0 SECTION does not.

WHY IT MATTERS HERE, SPECIFICALLY. The shipped CHANGELOG.md carries a 0.1.0 section whose single bullet says the chapters hold 'verbatim Claude Code documentation chapters'. The absolute-path series established that word is WRONG (the chapters are adapted, not verbatim), and the correction was deliberately routed to the commit message because CHANGELOG.md is regenerated by the pipeline and hand-written prose in it does not survive a publish. The next publish therefore DOES NOT ERASE THE FALSE WORD — it erases the 0.1.0 SECTION ENTIRELY, along with the 0.1.0 release's only record. The false word and its context vanish together, and a reader of the next CHANGELOG sees a 0.2.0 with no prior release listed.

THE SECOND HAZARD. The version-bump path that would normally protect a released entry is untested on this repository: the repository has no tags, so there is no tag for --bump to protect, and cliff.toml's body template renders the unreleased window as a dated version heading. A release cut before e25b03e (the commit that introduced the pipeline) yields a CHANGELOG with no 0.1.0 section at all.

WHAT IS PROPOSED, AND WHAT IS NOT. Nothing is proposed here beyond recording the defect, because the fix is a publish-path decision: either tag the repository so --bump has an anchor, or change the pipeline so the prior section is preserved, or accept the loss explicitly and move the 0.1.0 record somewhere that is not regenerated. The first option is one git command and is the smallest change; the second is a change to stage_changelog and its own docstring states the constraints (-o overwrites, --unreleased truncates, --prepend accumulates). Deciding is the owner's.

REPRODUCTION (read-only, on a clone in /tmp, not on the working tree): git clone <this repo> /tmp/cliff-test; cd /tmp/cliff-test; git cliff --bump --tag v0.2.0 -o /tmp/cliff-out.md; grep -c 0.1.0 /tmp/cliff-out.md  # 0.
