## Cell conventions

- **Acceptance cell** = the unit's criterion, then its reported verdict after an em-dash: `<criterion> — REPORTED:/VERIFIED: <verdict>`. The criterion text is the template from this ledger's first version (`git show 4840d96:DELEGATION.md`), identical across the four cohort rows; it describes the report's required FORMAT, not a per-unit threshold. The per-unit scope lives in the Files column (which skills, which range), and the verdict is what the run found.
- **Status cell** = the outcome and the report path, and the only place a report path belongs.
- Row 4's report path was in both cells in df69583; the Acceptance-cell copy was removed in 25583d9. One path, one cell.

The finding that changed the design: Claude Code injects the full content of "the first 32 distinct names in the list" (code.claude.com/docs/en/sub-agents), and the agent lists 64, so the frontmatter ORDER selects which 32 skills get their content injected — order is load-bearing, not cosmetic. What the docs do not state is what the remaining names receive: the `skills` field controls what is PRELOADED, not what is ACCESSIBLE ("the subagent can still discover and invoke project, user, and plugin skills through the Skill tool"), so a skill past the window has no content injected but stays invocable — the cost is context, not capability. Which 32 to preload is a product decision: the agent's frontmatter is authoritative (its first 32 names are the preload set) and `tests/test_skills_menu.py` mirrors that window. The mirror is not redundant with the frontmatter/body order check: a coordinated edit that shifts the window (adding a skill to the frontmatter, the body index and the README in the same place) leaves every other check green, because both copies of the routing order still agree — the mirror is the only check that sees the window move. Reordering the frontmatter's tail stays free.
