## Cell conventions

- **Acceptance cell** = the unit's criterion, then its reported verdict after an em-dash: `<criterion> — REPORTED:/VERIFIED: <verdict>`. The criterion text is the template from this ledger's first version (`git show 4840d96:DELEGATION.md`), identical across the four cohort rows; it describes the report's required FORMAT, not a per-unit threshold. The per-unit scope lives in the Files column (which skills, which range), and the verdict is what the run found.
- **Status cell** = the outcome and the report path, and the only place a report path belongs.

- Regression guard for the adapted paths: ONE rule over the whole tracked tree, in `tests/test_skills_menu.py` — a path segment under a home directory that is NOT on the known-not-a-name list is treated as a NAME, and no readable tracked file may contain one. It is ONE rule, not three, because the scoped versions missed a failure mode this series hit twice: a literal home path in any tracked DOCUMENT (a chapter, the ledger, the README) is a CPV MAJOR, and a chapters-only rule cannot see the ledger. (Both occurrences were in DELEGATION.md, at two lines; the point is that a rule scoped to chapters could not have seen either.) (CPV exempts `tests/*.py` as inert data, so the test file was never a finding — but it IS excluded from the plugin's own rule, because the rule covers shipped files, not the suite that checks them.)
- WHAT THE RULE ACTUALLY IS, stated plainly: a SHORT LIST OF SPELLINGS KNOWN NOT TO BE NAMES. "Reads as a real name" is a semantic property and is not decidable by a lookup table, so the honest form of the rule is "a segment not on this list is treated as a name", and that is now what the docstring says as well as the ledger. The list is the corpus's own vocabulary — the account tokens the upstream text uses for "your account", plus the two project names it uses — and it is deliberately NOT extended speculatively: a role account like `admin` reads as a role rather than a person and would be a reasonable addition, but nothing in the corpus uses one, and pre-adding spellings that nothing uses is how a list stops being a judgement and becomes a superstition. The rule is CONSERVATIVE on purpose: the cost of a false positive is one line in one list, the cost of a false negative is shipping somebody's name. When a false positive lands on a re-synced file, the answer is a judgement about THAT value — add it to the list if it is a placeholder, change the example if it is a name — and never a blanket exemption; a blanket exemption is the fitted list this series exists to remove. It is NOT extended by shape either — no shape test can tell a project from a person, since one that accepts `my-project` also accepts `myra`.
- The rule's COVERAGE is every readable tracked file — no extension allowlist, because an earlier version skipped 6 tracked files, including NOTICE and LICENSE, which the plugin ships (verified by injecting a personal name into NOTICE and watching the guard catch it). Its only exclusion is the `tests/` tree, where a file may legitimately NAME the values it asserts are absent. There is deliberately NO file-type exclusion: an earlier version had one for four machine artefacts (a lockfile, an ignore list, a version pin, a git hook) and it defended nothing — none of the four contained a home path at all — while it excluded a git hook that a maintainer reads, which the rule's own justification includes. A second list of filenames is the same fitted-list pattern this series removed from the spelling rule, on the other axis; one list is enough. The durable statement is the RULE, not the count: every readable tracked file, except the `tests/` tree. (At the time of writing, 208 of the 210 tracked files — a snapshot that goes stale when a file is added, which is exactly why the rule is what is written here.)
- KNOWN LIMITS, recorded here rather than left implicit: the file list comes from the git INDEX, so a file present but not yet `git add`ed is invisible (and is not shipped in that state); and a tracked file that is unreadable (deleted from the working tree, or binary) is skipped rather than reported.
- The guard EXCLUDES NOTHING from validation. It scans every readable tracked file, and where it over-flags it over-flags rather than narrowing its reach — a conservative false positive costs one line in one list, a narrowing costs coverage the plugin does not get back. Uniform coverage is the policy-aligned choice, and the cost of over-flagging is paid deliberately. This is why the four-filename exclusion was dropped: not because the four files happened to be clean, but because a file list is a second fitted list and the strict choice was the right one. Two boundaries on that claim, so it is not read as more than it is: the guard never suppresses a scanner finding and never narrows a scanner rule — that is what "excludes nothing" means here, and it is a statement about the GUARD, not about the scan (72 findings still stand, and 8 upstream paths were deliberately left alone). And the guard judges NAMES by the plugin's own judgement, but the SHAPE it inspects is a home path — and it now inspects all three shapes the corpus uses (`/Users/`, `/home/`, `C:/Users/`), so a name behind any of them is caught. It is not independent of the scanner in every respect: a CPV release that recognised a home-path shape the plugin does not would widen this guard's blindness the same way, so the shapes are a known limit, not a solved problem.
- WHEN TO REOPEN THE GUARD, so a future session need not re-derive it: (1) a re-sync introduces a personal name in a shipped document and the guard does NOT catch it — the mechanism is broken, investigate the mechanism, not the list; (2) a re-sync introduces a name-like segment the rule flags and a human calls it a false positive — that needs a SCOPE or WORDING decision made once, recorded, preferring changing the example over extending the list; (3) a CPV release changes the absolute-path rule — then the whole artifact series must be re-measured, because its premise (a MAJOR that cannot be fixed without breaking the example) disappears; (4) a new category of machine-GENERATED tracked file appears that records filesystem paths — the case the uniform rule handles worst, and it warrants the scope principle being re-stated as a PRINCIPLE, not a filename list.
